## Архитектура

**Телефон как логин.** Firebase Auth не поддерживает "телефон+пароль" как
метод — только email+пароль или email+SMS-телефон (Phone Auth, платный,
с SMS). Решение: номер телефона превращается в синтетический email вида
`<цифры>@employees.icon-finance.local` — сотрудник видит и вводит только
номер, `signInWithEmailAndPassword`/`createUserWithEmailAndPassword`
получают этот сконструированный email под капотом.

**Второй Firebase App instance для создания сотрудников.** Клиентский SDK
после `createUserWithEmailAndPassword` автоматически подменяет текущую
сессию на нового пользователя — при каждом добавлении сотрудника админ
вылетал бы из своего же аккаунта. Фикс: отдельный
`firebase.initializeApp(firebaseConfig, 'employeeCreator')` с собственным
`.auth()`, используется только для создания аккаунта сотрудника; сразу
после создания на этом instance вызывается `.signOut()` (чистит его
внутреннюю сессию, не трогает основную). Основная сессия админа (`auth`,
без имени instance) не участвует в создании и не меняется.

**`disabled`-гейт вместо удаления.** Без backend (Cloud Functions/Admin
SDK) нельзя по-настоящему удалить чужой Auth-аккаунт с клиента. Вместо
этого: у каждого сотрудника есть Firestore-документ
`employees/{uid}` с полем `disabled`. После входа сотрудника
приложение читает этот документ; если `disabled: true` или документа
нет вовсе — тут же `auth.signOut()` + сообщение "Аккаунт отключён".
Логин-пароль технически всё ещё "работает", но зайти в приложение с ним
нельзя. Собственный аккаунт админа (email) в `employees` не заводится —
им по-прежнему управляет только `admins/{uid}`, эта часть не меняется.

**Побочный эффект отказа от саморегистрации:** любые уже существующие
самозарегистрированные (не через это Добавление) аккаунты, если такие
есть, тоже не будут проходить `employees`-гейт после этого изменения и
потеряют доступ — это ожидаемо, соответствует цели "доступ только через
админа".

## Экран входа

Убрать блок "Нет аккаунта? Зарегистрироваться" и весь `authMode ===
'register'` путь ([app.js:1393](../../../app.js#L1393),
[app.js:1417](../../../app.js#L1417),
[app.js:1421-1423](../../../app.js#L1421),
[app.js:1440-1447](../../../app.js#L1440)) — экран всегда в режиме
"Вход".

Добавить переключатель способа входа прямо над полями формы:
`[Email] [Телефон]` (два таб-кнопки, локальное состояние `authLoginMode:
'email' | 'phone'`). В режиме email — как сейчас (`<input
type="email">`). В режиме телефон — `<input type="tel">` с префиксом
`+998` (как в макете), под капотом при сабмите номер очищается до цифр и
оборачивается в синтетический email перед вызовом
`signInWithEmailAndPassword`.

После успешного входа (`onAuthStateChanged`), если у пользователя нет
записи в `admins` — читаем `employees/{uid}`:
- документа нет или `disabled: true` → `auth.signOut()`, показать
  `authError = 'Аккаунт отключён или не найден.'`, остаться на экране
  входа;
- иначе → `enterApp(uid, employeeDoc.role === 'admin')` — права
  сотрудника-админа приходят из его же `employees`-документа, не из
  `admins` (та коллекция клиентом не пишется вообще, см. "Права в
  Firestore rules" ниже).

## Настройки (admin-only)

Новая кнопка "⚙ Настройки" в `.panel-head-actions` рядом с "Перейти к
новому месяцу" (тот же `admin-only` класс). Открывает модалку (тот же
паттерн, что уже есть у row-menu — фиксированный оверлей) с двумя
секциями:

**Тема.** Тот же тумблер, что и сейчас в правом нижнем углу
(`#themeToggle`) — дублируется сюда как ещё один переключатель на тот
же `localStorage`-ключ `cf_theme`; существующая кнопка-шарик в углу не
убирается (мелкая, не мешает).

**Сотрудники.** Список карточек — имя, должность, телефон, права
(Просмотр/Админ), тумблер Включён/Отключён. Кнопка "+ Добавить
сотрудника" открывает форму по макету:
- Имя (текст)
- Должность (select: Администратор / Учитель / Бухгалтер / Другое —
  просто подпись для списка, не влияет на права)
- Телефон (`+998` + цифры)
- Пароль (по умолчанию = сами цифры телефона, редактируемо)
- Права (select: Просмотр / Админ)

Поле "карточка"/привязка из макета не переносится — ссылается на
сущность из другого приложения, которой здесь нет.

Сабмит: через secondary app instance создаётся Auth-аккаунт
(синтетический email из телефона + пароль), затем в основной `db`
пишется `employees/{uid}: {name, position, phone, role, disabled: false,
createdAt}`.

Список сотрудников читается через `db.collection('employees').onSnapshot(...)`
(тот же паттерн live-подписки, что уже есть для `cashflow/*`).
Тумблер Включён/Отключён — `update({disabled: !current})` на
`employees/{uid}`.

**`admins` коллекция не трогается клиентом вообще** — её правило
`allow write: if false` в [firestore.rules](../../../firestore.rules)
специально жёсткое ("никто не может сам себя назначить админом"), это
не меняем. Вместо записи туда, admin-права сотрудника определяются
только через `employees/{uid}.role === 'admin' && !disabled` —
отдельный, второй путь к правам админа, параллельный существующему
`admins/{uid}`. И клиентская проверка (`state.isAdmin` в app.js), и
серверные Firestore rules должны понимать оба пути одинаково — см.
ниже "Права в Firestore rules".

### Права в Firestore rules

Функция `isAdmin()` в [firestore.rules](../../../firestore.rules#L5) сейчас
проверяет только `admins/{uid}`. Расширяется до:

```
function isAdmin() {
  return request.auth != null && (
    exists(/databases/$(database)/documents/admins/$(request.auth.uid)) ||
    (
      exists(/databases/$(database)/documents/employees/$(request.auth.uid)) &&
      get(/databases/$(database)/documents/employees/$(request.auth.uid)).data.role == 'admin' &&
      get(/databases/$(database)/documents/employees/$(request.auth.uid)).data.disabled != true
    )
  );
}
```

Без этого сотрудник с `role:'admin'` видел бы кнопки редактирования на
клиенте, но каждая запись в `cashflow/*` реально отклонялась бы
сервером — тихо ломало бы приложение, а не просто "не хватает фичи".

Новая коллекция `employees`:
```
match /employees/{userId} {
  allow get: if isAdmin() || (request.auth != null && request.auth.uid == userId);
  allow list: if isAdmin();
  allow write: if isAdmin();
}
```
Сотрудник может прочитать только свой документ (нужно для
`disabled`-гейта при входе), листинг всей коллекции — только админу
(для списка в Настройках). Писать (создать/отключить/сменить роль) —
только админ.

## Вне рамок

- Реальный SMS-вход (Firebase Phone Auth) — отклонено пользователем,
  не делаем.
- Настоящее удаление Auth-аккаунта сотрудника — требует Cloud
  Functions/Admin SDK, вне рамок; используется `disabled`-флаг.
- Редактируемый список должностей в Настройках — фиксированный список
  из 4 значений, без своего UI управления.
